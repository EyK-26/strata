# Replacing checked-in dogfood apps with generated acceptance fixtures

Strata owns framework mechanisms, generator output and their pre-release acceptance tests. [strata-shop](https://github.com/EyK-26/strata-shop) is the external product dogfood and consumes published packages. Its commerce rules and Postgres-only deployment do not replace framework dialect, feature-combination or package acceptance.

## First PR: preserve the security suite

`bun run test:e2e` now generates an external temporary server-HTMX/Postgres/RLS/cookie-token-JWT app with MFA, verification, SCIM and metrics. It installs the candidate core/bootstrap/cli tarballs, explicitly installs the optional SAML peer at the framework lockfile-installed version exercised by the suite, migrates and explicitly seeds an owned database, and boots the generated runtime with the restricted `strata_app` role. It never copies or imports `apps/hiroapp`. The two RLS-context probes resolve the same packed package instance used by the app; importing the monorepo's source alias would test a separate connection/context registry.

The former `tests/e2e/hiroapp.security.test.ts` is moved to `tests/e2e/generatedApp.security.test.ts`. Its 23 test names and 116 static assertion statements are unchanged from `ed98f3b32d32ebc2827a87cd9d32676c73f633cb`; both baseline and generated-app runs execute 115 assertions, with 23 passes, zero failures and zero skips. A TypeScript AST/printer comparison confirms identical ordered test names and assertion statements (normalized SHA-256 `6d9b9be8d01cbe206aaf72b2d72606fb5a4b382ae5780953e8026b6d8ffa3618`). The static/runtime counts differ because a conditional assertion branch is not selected in this configuration; no assertion was removed.

The first generated run failed 4 cases: three tenant fixture inserts depended on old app-owned `plan`/`region` columns absent from the current generic generated tenant schema, and SAML depended on the monorepo's optional peer. The fixture inserts now write the same tenant slugs without those unrelated columns, and the test app explicitly installs the SAML peer. Security expectations, response contracts, RLS grants/denials, signatures and replay checks are unchanged. The corrected generated run passes all 23 cases and 115 assertions. This is a harness migration, not a framework mechanism workaround.

The app context and pools close before the owned database is dropped and the temporary installation is removed. Failed setup also retains a cleanup path. Existing HiroApp databases, application directories and smoke/OpenAPI wiring remain in this PR. The helper fails rather than skipping when required infrastructure or installation is unavailable.

`validate:ci` includes `test:e2e` after the existing core coverage gate; both main CI and the release workflow use that command. The old duplicate main-CI invocation is removed. The coverage file scope, exemption ceiling, enforced-file line threshold and existing generated-app compiler matrix are unchanged. Packed-app security acceptance is a separate runtime gate; its assertion count is not a claim of source line coverage.

## Removal gates and subsequent focused PRs

1. Replace the remaining checked-in-app boot/OpenAPI/HTTP smoke dependencies with generated temporary fixtures. Preserve the current route inventory, API-only scope assertions, built SPA checks, integration extras and executable Docker behavior. Review root CLI/bootstrap dispatch, module preloads, test setup and environment helpers; do not change the published app CLI contract to emulate an in-repo demo.
2. Once those replacements pass, remove `apps/hiroapp`, `apps/hiroapp-hobby` and `apps/hiroapp-team`, their workspace/lockfile/Docker copies and obsolete special-case selectors. Reconcile the example presets, regeneration scripts, coverage exclusions and documentation by actual dependency, not by deleting every filename containing HiroApp. For example, the model parity unit suite is synthetic framework coverage and must survive the removal even if renamed.
3. Keep small deterministic framework fixtures and the SQLite/MySQL/Postgres generated-app matrix. Keep the external shop independent of framework checkout layout. Run all existing package/export, generator/type, unit/integration, E2E, smoke, coverage and release gates before claiming removal complete.

The checked-in apps must remain until their remaining executable gates have replacements. Local generated-app acceptance does not qualify external providers, shop capacity, a 24-hour soak, production recovery or independent security review.

## Second PR: generated CLI/OpenAPI and HTTP smoke

`verify:generated-runtime` runs two discoverable native Bun cases in `tests/e2e/generatedRuntime.test.ts`; each invokes an isolated verifier process that provisions the same disposable generated fixture and invokes its packed `strata` CLI for explicit migrate/seed, OpenAPI generation/validation/checking, and HTTP startup. Native startup must advertise a listening socket, pass the unchanged health/readiness/metrics/login and WebView smoke scripts, then exit cleanly after SIGTERM. The HTTP profile explicitly uses Redis cache regardless of the unit-test cache setting, and readiness must independently report database/Redis `ok`, never skipped Redis. The owned CLI HTTP fixture enables debug diagnostics for that observation; ordinary `APP_DEBUG=false` readiness correctly hides the checks, and the unchanged security suite retains debug-off behavior. A missing metrics token must retain the framework's concealment response (404). Commands, startup and shutdown are bounded; after a forced kill/timeout or interrupted run inspect owned fixture namespaces rather than assuming cleanup completed. Diagnostics are bounded for the long-lived server, and the owned database/install are removed on failure. Generated child environments explicitly omit `DOGFOOD_APP`, `HIROAPP_TEST` and `STRATA_SCHEMA`.

There is a correction to the earlier API-only claim: the legacy private adapter cleared route metadata and relabelled every handler as API. The previous 40-operation document included 18 HTML operations. Passing its old snapshot check did **not** prove API-only scope. The adapter now delegates filtering to the existing official `registerAppOpenApiRoutes`, preserves metadata, and closes its context/database after observation; no public framework filtering implementation is forked or changed.

The corrected snapshot has **22 API/protocol operations**, including SAML protocol endpoints, and excludes HTML login/account/reset/verification pages and the HTML root. All **40 runtime operations** remain checked separately against `tests/fixtures/generated-runtime-routes.json`, frozen from the pre-change snapshot. A generated bootstrap probe observes the real route registry/map using public APIs; it does not replace routes or change the generated app. The native generated CLI must match the committed API-only snapshot byte-for-byte, reject deliberately introduced drift, and pass again after restoration. Route removal is not hidden by shrinking the OpenAPI document.

The five OpenAPI command unit cases now exercise official command factories with a deterministic route fixture instead of booting HiroApp. Their ordered names and all 17 static assertion statements are unchanged (normalized SHA-256 `d585a97860c76b121ef8ef68798ec726141e2b2b443835618dc0fc652e0f89d6`); the focused ten-case command/filter suite passes all 26 executed assertions. The original smoke-test and WebView assertions remain unchanged. Integration-extra OAuth/OIDC/Stripe and built-SPA assertions also remain intact.

`validate:ci` runs the existing coverage gate, all 25 native E2E cases (23 unchanged security cases plus two generated runtime profiles), then the unchanged integration-extra/built-SPA smoke scripts. `bun run smoke` selects both native runtime profiles plus those extra scripts for an independent focused run. Thus release validation now includes the HTTP/extras/SPA smoke checks too. Main CI removes only its redundant fixed-port HiroApp daemon and duplicate smoke invocation; dependency audit remains a separate required step. No app directory, Docker/workspace wiring, remaining legacy migration/CLI loader, compiler combination, coverage threshold or exemption is removed here. Those dependencies still need the final removal PR and full qualification.

Second-stage final host acceptance passes 2,348 unit/integration tests, zero failures and the same three existing skips; core coverage remains 136 enforced / 274 exempt. ## Third PR: generated source regression fixtures

The Eta, login-throttle wiring and request-path RLS fence suites now generate the same RLS and team layer profiles instead of reading the checked-in apps. Their source-only fixtures live in owned temporary directories under `node_modules/.cache`, inherit the workspace's package resolution, and are removed by `afterAll` or failed setup. They neither install packages nor boot an application: executable package acceptance remains in the isolated packed-app E2E gates. Existing example preset names remain supported; removing directories does not require deleting the preset API or its tests.

`tests/fixtures/generated-source-files.json` freezes all 52 existing view/module/bootstrap paths from `cda5a84`. Fixture creation refuses any missing file; generated views additionally retain the previous 10/6 minimum counts, and every scanned request-path root must be non-empty. The original per-file checks still run on every emitted file, including any additional generated files. An absent directory cannot silently pass the generated-source checks.

The failed-job identity migration suite retains a byte-identical historical upgrade definition in `tests/fixtures/migrations/failedJobIdentity.ts`. Current starters create `job_id` in their initial schema, so generating a new app would not reproduce the populated pre-upgrade table. The fixture preserves that old schema transition and every existing SQLite/MySQL/Postgres upgrade, old-writer, identity-write and rollback assertion; it is test history, not a second production migration mechanism. The separate framework fixture migration remains exercised too.

An ordered TypeScript AST comparison against `cda5a84` verifies that all 89 original static assertion statements in the four changed suites remain unchanged and in order. Two additional statements exercise the non-empty/minimum-size guards (repeated across roots). The two case descriptions naming checked-in HiroApp are renamed to describe generated output; no cases are removed. The historical migration body is byte-identical to the old app definition. The focused run passes all 23 cases, including all three real database engines, with zero failures/skips and 260 executed assertions.

The app directories, runtime/CLI selectors, Docker image, workspace entries, core coverage policy and all synthetic model-parity cases remain intact. Their final cleanup is a separate PR after the replacement gates pass. This source migration does not claim Docker retirement or complete app removal, and needs no package version bump.

Third-stage `validate:host` passes 2,348 unit/integration cases with zero failures and the same three existing engine/platform skips; coverage remains 136 enforced files and 274 exemptions. All 25 native E2E cases pass without skips, followed by integration-extra and built-SPA smoke checks. All 18 generated compiler combinations and package/export/release/type/lint gates pass. ## Fourth PR: private fixture CLI and executable Docker replacement

The repository CLI explicitly manages framework fixtures; its database commands require `STRATA_SCHEMA=fixture` and use the existing framework environment policy to reject production/staging, including `NODE_ENV=production`, before database access. It no longer delegates to HiroApp or auto-seeds after ordinary migrate. Root CLI OpenAPI commands delegate to the official public command factories, removing the duplicate generate/validate/drift contracts. OpenAPI/SDK command tests use an explicit two-route fixture through the official API-only filtering helper; the committed 22-operation generated-app snapshot and independent 40-operation runtime inventory remain checked by the packed-app acceptance cases. They are not replaced with the small command fixture.

The old app dispatch/server entrypoints are removed. Module preloads explicitly select empty framework fixtures. Two CLI suites had implicitly relied on an earlier app boot to configure discovery: an initial shared-process focused run failed four cases after that coupling was removed. Both suites now declare their empty module manifest explicitly; all six case names and 18 original static assertion statements are unchanged in an AST comparison against `0e5cac3`. The corrected shared-process CLI run passes 245 cases (including the new fixture boundary case), and the original 244-case isolated run passes too. No application/provider lifecycle mechanism is substituted.

The root Dockerfile generates a temporary server-HTMX/Postgres/RLS/cookie-token-JWT app from current starter output, packs candidate core/bootstrap/cli packages and installs them into that external app. The release image contains that generated installation only. Checked-in apps are excluded from build input and removed from root workspaces/lockfile. Contributor Compose provides infrastructure only. Optional production/staging acceptance configurations keep admin credentials in a separate explicit migration service and never seed at startup. They remain manual acceptance examples, not qualified product deployment manifests.

`tests/e2e/generatedDocker.test.ts` is a required, discoverable native Bun case included in main/release validation. Its isolated verifier provisions an owned Postgres container, Redis container, network, random credentials and a uniquely tagged candidate image. It exercises production migration and seeding refusal, explicit development-only fixture seeding, repeat migration, production secret/live-role checks, Docker health, existing HTTP/WebView smoke scripts, metrics concealment, CSRF, Redis loss/recovery and SIGTERM shutdown. Compose configurations are resolved and checked for admin/runtime credential separation and absence of implicit migration/seeding commands. Every required dependency must work; no new skip is introduced.

Production tenancy correctly refuses the Docker loopback host and untrusted forwarded-host input. Both denials are asserted. A loopback-only test edge supplies the configured public authority for the unchanged smoke scripts, forwarding requests to the actual published Docker port; it does not alter generated tenant policy or response bodies. This is transport for a virtual-host fixture without external DNS, not an app routing workaround or proof of TLS/browser-auth deployment qualification. HTTP/workers receive no migration credentials.

Initial Docker attempts exposed harness configuration issues: `NODE_ENV=production` correctly refused demo seeding despite `APP_ENV=local`; the production guard correctly rejected a localhost `APP_URL`; and the contributor Redis container had no Docker network attachment, so readiness correctly returned 503 from the generated image. The verifier now keeps the production refusal assertion, supplies complete valid production test configuration, and owns Redis/network infrastructure rather than changing the existing service. The focused Docker acceptance subsequently passes, including the intentional Redis outage/recovery. No production guard or existing smoke assertion was relaxed. Forced verifier termination can bypass normal cleanup; inspect its owned `strata-docker-*` resources and `strata-acceptance:*` tags after interruption.

The two removed private entrypoints were already excluded from source coverage. Their stale exclusions are removed from both ignore lists and the exemption ceiling is ratcheted from 274 to 272; the 136 enforced files and their 100% line threshold are unchanged. All app directories, legacy example presets/generation options and synthetic model-parity tests remain for the final physical-removal/documentation PR. This step needs no framework package publication; the batch release notes/bump belong on that final PR.

Fourth-stage host validation passes 2,349 unit/integration cases, zero failures and the same three existing skips, with 136 enforced files / 272 exemptions. All 26 native E2E cases pass without skips (the original 25 plus Docker acceptance), followed by unchanged integration-extra and built-SPA smoke checks.
