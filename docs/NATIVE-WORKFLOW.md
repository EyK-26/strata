# Models, migrations and views

This workflow uses the official generated server-HTMX app, its installed CLI and public framework APIs. It requires a release containing `make:model`, `make:view` and the UUID builder; older apps must deliberately add the commands to their app-owned CLI registry as described in [STARTER.md](STARTER.md#scaffold-commands-make). Installing a package does not rewrite generated source.

## Generate and describe a model

From the generated app directory:

```sh
bunx strata make:model Contact --table=workflow_contacts --key-type=string
bunx strata make:migration create_workflow_contacts
```

The commands create separate files. Edit `src/models/Contact.ts` to add the domain field to all three declarations:

```typescript
import { defineModel } from "@getstrata/core/database/model";
import { defineTable } from "@getstrata/core/database/table";

interface ContactRecord { id: string; name: string }
const table = defineTable<ContactRecord, "id">({
  name: "workflow_contacts",
  primaryKey: "id",
  columns: ["id", "name"],
});
export class Contact extends defineModel(table) {
  static override $fillable = ["id", "name"] as const;
  static override $timestamps = false;
}
```

Generated startup discovers the model under `src/models` and supplies its repository. No custom repository or `register.ts` edit is needed. Keep the allowlist explicit. Use application validation and authorization before mass assignment; timestamps remain off until their columns are declared.

## Define the migration explicitly

Keep the generated migration's name, imports, driver selection and up/down structure. Replace its up callback body with:

```typescript
schema.create("workflow_contacts", (table) => {
  table.uuid("id").primary();
  table.string("name");
});
```

Its down callback uses `schema.drop("workflow_contacts")`. The generated callbacks run inside `Schema.run(db, resolveDatabaseDriver(), ...)`. Apply the migration with the app's migration identity:

```sh
bunx strata migrate
```

PostgreSQL stores this column as native UUID. MySQL uses `CHAR(36)` and SQLite uses `TEXT`; those two mappings do not impose PostgreSQL UUID validation or canonicalization. IDs are supplied explicitly, not generated by this column method. Existing UUIDs can be read and written without changing their column type or identifiers. See [UUID columns](DATABASE.md#uuid-schema-columns) for constraints and dialect limits.

Keep previously applied migration names/history stable. For an existing table, generate a new additive migration and retain existing identifiers; do not rerun a copied initial schema or replace applied history. Externally provisioned databases/roles can keep the existing public migration-runner path without invoking cluster role provisioning.

## Persist through the model and render a view

After the app has booted its model discovery:

```typescript
import { Contact } from "./src/models/Contact";

const contact = await Contact.create({ id: crypto.randomUUID(), name: "Příliš žluťoučký" });
await contact.update({ name: "Updated <contact>" });
const found = await Contact.find(contact.toObject().id);
// Contact.repository() is available for repository operations; no boilerplate subclass required.
```

Generate only a template:

```sh
bunx strata make:view contacts/show
```

The generated `views/contacts/show.eta` escapes `it.title` and `it.message`. An explicit minimal renderer is:

```typescript
import { EtaViewEngine, htmlResponse } from "@getstrata/core/view";

const engine = new EtaViewEngine("views");
const html = await engine.render("contacts/show", {
  title: found?.toObject().name,
  message: "Příliš žluťoučký",
}, { layout: false });
const response = htmlResponse(html);
```

In an existing HTTP handler, use the app's configured view renderer so its directory/layout data remain authoritative. Route registration and request authorization remain explicit; the generator adds neither. API-only apps still need an intentional view dependency/provider configuration.

The installed-candidate acceptance exercises model generation, deliberate domain edits, a separate UUID migration, automatic startup discovery, ORM create/find/update, template generation and escaped UTF-8 rendering on PostgreSQL, MySQL and SQLite. The form and provider boundaries are documented separately in [repeated form fields](BUILDING-APPS.md#repeated-form-fields) and [mail provider extensions](INTEGRATIONS.md#mail-provider-extensions).
