# Encryption rotation foundations

The framework now provides the primitives, auth configuration and explicit maintenance-mode rotation protocol for #140. Shop adoption, live backup/restore drills and independent security qualification remain separate work. By default, the generated email/MFA APIs still use the existing KMS_ENCRYPTION_KEY and enc:v1 contract. An explicit keyring now supports reader-first adoption through those official APIs. Do not replace that variable to rotate persisted auth data. The keyring/auth APIs never change schema or rewrite stored records. The explicit migration API below does so only when invoked by a trusted operator.

## Explicit keyring primitive

`createFieldEncryptionKeyring` is exported from `@getstrata/core/crypto/fieldEncryption`. Supply an active public key ID, a retained map of 1–32 AES-256 keys, a pinned lookup key, and optionally the explicit original key for unidentified enc:v1 ciphertext. Keys are 32-byte Uint8Arrays, copied at construction; the returned API is immutable. Resolve secret material in application infrastructure, never source control. IDs and purposes are 1–64 ASCII letters, digits, underscores or hyphens. IDs are permanent identities: never assign different key material to an existing ID.

New writes use `enc:v2:<key-id>:<base64 payload>` with a random 96-bit nonce and a full 128-bit AES-GCM tag. Version, key ID and caller-supplied purpose are authenticated as associated data. Callers must keep purpose stable (for example `email` versus `mfa`). Retained-key reads support old and new write keys; the explicit legacy key reads v1 without trial-decrypting every retained key. Legacy v1 did not authenticate purpose, so that guarantee cannot be retroactively added until a record is re-encrypted. Plaintext, unknown versions, missing keys, noncanonical/truncated payloads and authentication failures reject. Errors exclude ciphertext, plaintext, key material and key identifiers. The implementation follows Node's [authenticated encryption API](https://nodejs.org/api/crypto.html#ciphersetaadbuffer-options).

`lookup(normalizedValue)` uses the separately pinned HMAC-SHA256 lookup key. Passing the original encryption key as lookupKey preserves existing normalized email hashes while write keys change. It does not normalize input itself. Never rotate this lookup key as a side effect of write-key rotation: persisted indexes, uniqueness and concurrent account operations need an explicit migration protocol. A lookup key must remain secret even when the historical encryption key is retired; separating future encryption keys does not erase that dependency.

## Boundaries for the remaining layers

Retaining keys lets a future configured reader decrypt previous writes; it does not make an old binary understand v2. All readers must support v2 before activating v2 writers, and rollback must target a compatible reader retaining all written key IDs. Configuration validation cannot determine that two separately deployed processes reused an ID with different bytes; enforce consistent immutable secret versions in deployment.

Auth integration must retain lookup compatibility and encrypted/plaintext policy without silent record rewriting. The migration must checkpoint only committed batches, compare original values before updating, serialize collisions and concurrent writes, preserve tenant/RLS boundaries, recover interrupted batches and keep failed records retryable without logging values. Key retirement must include live records, retained backups and restoration tests. Do not enable new auth writes or retire keys merely because primitive tests pass. Independent security review and deployment qualification remain required by the production plan.

## Auth configuration and reader-first rollout

The existing protectEmail/revealEmail, emailLookupForQuery and protectMfaSecret/revealMfaSecret APIs resolve an optional `KMS_ENCRYPTION_KEYRING` JSON object. Bootstrap and secrets:check validate it. Supply `activeKeyId`, `encryptionKeys` (ID to 32-byte hex or canonical base64), `lookupKey`, optional `legacyV1Key` and an explicit `writeVersion` of 1 or 2. Missing, malformed, oversized or unknown configuration options fail without echoing the configuration. KMS_ENCRYPTION_KEY and the keyring cannot both be set. No default keyring or secret is generated.

When adopting existing v1 email/MFA records, explicitly retain the original key as legacyV1Key and lookupKey. The configuration rejects different legacy/lookup keys: lookup-key rotation is not implemented by this API. writeVersion=1 requires legacyV1Key and keeps producing the original ciphertext format while all upgraded readers can read both versions. writeVersion=2 uses the active identified key for new writes. The independently pinned lookup key produces exactly the original normalized email hash. It must remain retained for query and uniqueness compatibility. Removing legacyV1Key does not prove records/backups no longer use it; it only makes such reads fail.

Deploy compatible readers with writeVersion=1 first. Verify every HTTP process, worker, command and restore tool uses the same immutable configuration and understands v2 before any writer switches to 2. Then activate v2 writers with all previous v2 IDs and the v1 key retained. This prepares the read/write contract; the explicit resumable migration and a fresh audit are required before retiring any key. Do not use the primitive or configuration alone as proof of safe retirement. Rollback to an upgraded binary in writeVersion=1 can still read v2; rollback to an older binary cannot. Restore historical backups with their retained keys and original lookup key.

Email uses the authenticated purpose `email`; MFA uses `mfa`. Keyring readers decrypt retained email ciphertext regardless of the write flag and always reject plaintext MFA. FEATURE_FIELD_ENCRYPTION=false keeps the existing plaintext-email write/lookup behavior; do not change that flag during a rotation of encrypted email indexes. MFA writes remain encrypted independently of that email flag. No successful read automatically rewrites a record, changes lookup indexes or migrates tenants. Unknown identified ciphertext without keyring configuration rejects rather than becoming plaintext. Resolution is stateless so independently bundled entrypoints and processes read the same explicit environment; changing a running process's environment is not a coordinated deployment procedure.

## Explicit maintenance-mode migration

The `@getstrata/core/crypto/fieldEncryptionRotation` subpath (also exported at the package root) provides `createFieldEncryptionRotationMigration(name, driver, { rls? })` and `runFieldEncryptionRotationBatch(options)`. Add the former as an explicit file migration; observation/auth boot never creates the checkpoint table. For Postgres RLS apps pass `rls: true` after the official RLS helper migration has been installed. The checkpoint policy uses the existing framework tenancy helpers; the runner never enables bypass. Give only the trusted administrative command the necessary database access. Do not expose this API as an unauthenticated route or give shoppers migration capabilities.

Stop admission and drain every HTTP process, worker, scheduler, admin script and other writer. This release supports maintenance-mode rotation, not an online lookup-key transition. `maintenanceMode: true` is the operator's assertion that this has happened; it is not a distributed admission control, authorization check or proof that writers have stopped. Keep them stopped through migration, a fresh audit and configuration promotion. Back up before changing records and keep historical keys. Configure readers on the compatible version before this procedure.

Create source and target keyrings from the trusted secret provider. The source retains keys needed to decrypt existing fields and the previous lookup key. The target has a new permanent active key ID and, if retiring the original lookup secret, a new independently generated lookup key. Pass a framework-bound plain/custom BaseRepository, unique ASCII runId, stable scopeId, explicit field descriptors, source, target, maintenanceMode and a bounded batchSize (1–500, default 100). Each descriptor identifies the storage column and authenticated purpose. An email descriptor can also identify its lookupColumn; the runner uses official normalizeEmail and validates the previous or target HMAC before moving the index to the target value. It never guesses which app table or column holds auth data. This is not a commerce model or an implicit accounts-table convention.

Only nonnegative safe integer primary-key values are supported by this initial runner; UUIDs, negative IDs and identities beyond Number.MAX_SAFE_INTEGER reject. The primary key must uniquely order rows within the chosen scope. It projects only the ID and declared fields, uses bounded continuation queries and includes soft-deleted records. NULL encrypted fields remain NULL and a corresponding lookup must also be NULL. Plaintext/malformed fields reject rather than being silently adopted. Confirm column widths can hold identified ciphertext; read-back checks detect coercion/truncation before the checkpoint advances. Bulk repository writes intentionally bypass hydration, password/field casts, model hooks and commerce events.

AbortSignal cancellation is cooperative between database operations; it cannot interrupt a pending SQL call. Configure database statement/lock and network timeouts, and an administrative command shutdown deadline. Resume from the persisted checkpoint after interruption.

One invocation processes one transaction. Row updates compare the original encrypted fields and lookup values, preserve unrelated columns, verify stored values, and advance a durable cursor in the same transaction. Checkpoint claims serialize runners with conditional writes. Schema/uniqueness/decryption/storage failures, cancellation or changed rows roll back the entire batch; it skips no failed record. Repair through an explicit administrative procedure, then resume the same run. A lost commit acknowledgement can have an uncertain outcome: rerun using the persisted checkpoint rather than assuming a failed response means no commit occurred. The cursor is canonical text to avoid driver-specific BIGINT hydration. No row ID, SQL, ciphertext, key material or driver details are included in failure messages.

Use a distinct runId/scopeId for each tenant or database partition. scopeId is an identity label, not a query filter: the runner scans the entire repository table visible through its database/RLS scope. For RLS, wrap **one batch at a time** in the official runWithTenantDatabase scope and await the outer commit before recording progress. The runner preserves that transaction and binds checkpoint definitions to the current tenant, table, fields, mode, target key ID and configuration probes. Reusing a run with a different definition or target keys fails. No tenant enumeration or administrative bypass is performed for you. Completed checkpoints describe that frozen migration run; they are not current database-wide retirement attestations.

## Promotion, audits, rollback and backups

While writers remain stopped, start a **fresh** runId with mode `audit`. It scans the declared fields without rewriting rows and rejects any previous-version/key ciphertext, incompatible lookup or authentication failure. Run the audit with source equal to target to prove the declared live data is readable and queryable without historical secrets. Audit every relevant table, tenant, partition, soft-deleted record and custom encrypted field. An omitted scope or field is not covered. A successful audit cannot attest to retained backups, replicas, exports or unobserved writes; keep an inventory and record that operational evidence separately.

After all fresh audits pass, promote the compatible auth configuration to writeVersion=2 with the target active key and lookup key. For a **lookup-key change**, omit legacyV1Key from the live configuration: the reader-first configuration deliberately rejects a different legacy/lookup pair. All declared live records must already be v2. Retained previous v2 keys can remain in encryptionKeys until their separate retirement evidence is complete. Keep the original legacy v1/lookup key in the protected historical backup key inventory, not in source control. Old backups are restored in an isolated environment using their original legacy configuration, migrated and audited to the current target keys **before** admitting traffic. Do not attach an old backup directly to the new live lookup configuration.

Before resuming writers, verify email lookup, MFA and uniqueness under the target runtime configuration. Do not change FEATURE_FIELD_ENCRYPTION during rotation. Do not roll the database back to old ciphertext while serving the new lookup configuration. For a planned key/data rollback during maintenance, start a new run with the current keyring as source and an identified retained key plus the prior lookup key as target; audit it and promote the corresponding compatible runtime configuration. Never reuse a key ID with different material or roll back to a binary that cannot read v2.

Remove a key from live decrypt configuration only when every declared live scope passes its fresh audit. Destroy historical key material only after every dependent backup/export/replica is migrated or expires, or after explicit intentional destruction approval. If a key was compromised, retaining it for old backups carries a continuing exposure: use an independently reviewed incident/backup re-encryption procedure. A pinned original lookup key is still a secret dependency; ciphertext-only rotation does not retire that secret. The explicit lookup-key migration above addresses live indexes during maintenance, but does not erase historical copies. Independent security review, production/PITR restoration and shop operational qualification remain promotion gates, not results inferred from integration tests.
